# ADR-034: Tiered Spec Review for Two-Stage Workflow Checkpoint

**Status**: Accepted
**Date**: 2025-10-15
**Leap**: 7 (Test-Driven Autonomy Enhancement)

## Context

The two-stage workflow (Leap 7, ADR-027) requires user approval before proceeding to implementation. However, the current approval checkpoint presents the FULL specification (often 500-1000+ lines), which:

1. **Slows rapid iteration**: Users must read entire spec to approve simple features
2. **Cognitive overload**: Too much detail for initial approval decision
3. **No progressive disclosure**: All-or-nothing information presentation

**User Pain Point**: "I just want to approve quickly for simple features, but I'm forced to read 20 pages of spec."

## Decision

Implement **three-tier progressive disclosure** for specification approval:

### Tier 1: Executive Summary (<25 lines, 30-second read)
- Mission statement
- Technical approach
- Test summary
- Deliverables
- Constitutional status (Articles I-V)
- Effort estimate
- Risk level

**Purpose**: Enable rapid approval for well-understood features

### Tier 2: Key Decisions (<50 lines, 2-minute read)
- 4-6 architectural decisions (title, choice, rationale, trade-offs)
- Security implications
- Dependencies
- Performance considerations

**Purpose**: Provide architectural context without full spec

### Tier 3: Full Specification (file path, interactive view)
- Complete spec.md with all details
- Interactive view command (`cat <file_path>`)

**Purpose**: Available for complex/high-risk features requiring deep review

### Auto-Approve Countdown (30 seconds, configurable)
- Displays Tier 1, starts countdown
- Any key press interrupts countdown
- User can approve (A), revise (R), view tiers (V), or quit (Q)
- Timeout → default action (approve)

**Rationale**:
- 80/20 rule: 80% of approvals need only Tier 1 (mission + tests)
- 15% need Tier 2 (architectural decisions)
- 5% need Tier 3 (full spec review)
- Auto-approve reduces friction for simple features

## Implementation

   - ANSI escape sanitization
   - Color coding: ✅⚠️🔴 (constitutional status), 🟢🟡🔴 (risk)

4. **Integration** (`tools/orchestrator/two_stage_orchestrator.py`):

### Performance:

- UI rendering: <500ms (string formatting)
- Memory: Negligible (<1KB TieredSpec model)

### Security:
- **XSS Prevention**: HTML escape all spec content before rendering
- **Path Traversal**: Normalize file paths (no ../ sequences)
- **ANSI Injection**: Strip terminal escape sequences from user content
- **Timeout Abuse**: Enforce min/max bounds (10s-300s)

## Consequences

### Positive:
✅ **30-second approval** for simple features (vs 5-10 minutes full spec review)
✅ **Progressive disclosure** reduces cognitive load
✅ **Backward compatible** via config flag (`enable_tiered_review: false`)
✅ **Graceful degradation** to legacy approval on tier generation failure
✅ **Constitutional compliance** (Articles I-V validated in Tier 1)
✅ **VectorStore learning** tracks tier usage patterns (Article IV)

### Negative:
⚠️ **Deterministic parsing limitations**: May miss non-standard spec formats
⚠️ **Unix-only** (select() not available on Windows - would need msvcrt)
⚠️ **False approvals risk**: Users may approve without reading Tier 1 (mitigated by displaying summary first)

### Mitigations:
1. **Parsing failures** → Graceful fallback to legacy approval (WARNING log level)
2. **Windows support** → Future: Add msvcrt polling or threading fallback
3. **False approvals** → Tier 1 displays constitutional status (⚠️/🔴 warnings visible)

## Alternatives Considered

### Alternative 1: LLM-based summarization
- **Rejected**: Too slow (5-10s), costs tokens, non-deterministic
- **Trade-off**: Better summaries vs speed/cost/reliability

### Alternative 2: Immediate approval (no tiers)
- **Rejected**: Violates Article I (complete context before action)
- **Trade-off**: Fastest but unsafe (no spec visibility)

### Alternative 3: Collapsible sections (Markdown rendering)
- **Rejected**: Requires HTML/GUI (Agency is CLI-first)
- **Trade-off**: Better UX but breaks CLI workflow
